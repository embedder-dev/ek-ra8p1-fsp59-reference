# RA8P1 follow-up: FSP 5.9 register and driver compatibility

## Outcome and retained boundaries

Prioritize source/API compatibility before further feature work. Correct the existing custom FSP 5.9-derived RA8P1 candidate so applications use FSP's register vocabulary, standard interfaces and generated instances. Continue from the current candidate and retained r008 evidence; do not restart migration, expect a pristine support area, reset the nested baseline or restore stock packs. Earlier build/test results remain historical evidence, not proof of this broader compatibility requirement.

Retain the accepted architecture and safety decisions: R7KA8P1KFLCAC; CPU0 CM85/CPU1 CM33; 24 MHz crystal; ADC16H through ADC_B; exclusive core ownership of shared peripherals; CPU0-owned shared initialization/option words; physically disjoint MRAM/SRAM allocations and checked TCM aliases; reserved MRAM write windows and privileged-command opt-in. No hardware operations, probing, flash, reset, debugger or serial capture. All hardware criteria remain unverified.

Use only original FSP 5.9 sources/packs, the current candidate's owning files, RA8P1 manuals/technical updates and the supplied immutable pin model. Other RA8 headers establish spelling and C structure, never target addresses or semantics. Do not use the loaded RA8P1 SVD or any newer header/driver/MDF as evidence. Preserve pin-model filenames/bytes. Follow `MIGRATION.md` and `embedder.md`; change owning `baseline/ra/`, `baseline/module_descriptions/`, register inventories/generator and pack inputs, not generated projects or the IDE support tree.

## Findings that drive the correction

- The header is intentionally a partial register catalogue (`tools/ra8p1/generate_device_header.py:1–7,188–192`). Existing layout tests establish selected offsets/masks but do not establish stock-driver compatibility. Extend the inventory and generator rather than layering application shims over missing definitions.
- The header audit identifies missing GPT/SCI/SPI blocks and DMAC channel types/instances. Stock `r_dmac.c:29–30` expects `R_DMAC0_Type`, `R_DMAC0` and `R_DMAC1`; the inventory currently supplies only the global `R_DMA_Type`. Add the real channels without renaming or removing the global DMA controller.
- Stock `r_elc.c:106,174` expects `ELSR[i].HA` and `ELSEGR[event].BY`. Those arrays are missing from the target inventory although HM §20.2.2–3, pp.829–830 documents them. This is an owning-header omission, not grounds for a replacement ELC driver. Emit the baseline cluster/view names at the documented target offsets/strides, including all four software-event registers and the reserved holes in the ELSR span.
- `r_icu.c:32–44` expects split `IRQCRa`/`IRQCRb` arrays in `R_ICU`; HM §14.2.12, pp.539–540 places them in `ICU_COMMON`. Emit correct array views in `R_ICU_COMMON_Type`, then capability-gate the shared driver's register owner selection. Do not remap `R_ICU` and thereby corrupt its CPU-local NMI/event-bank accesses.
- HM Appendix 5, p.4293 explicitly maps SCI→SCI_B, SPI→SPI_B, ADC16H→ADC_B and DAC12→DAC_B. **Accepted decision:** qualify the hardware-correct variants (`r_sci_b_uart`, `r_spi_b`, `r_adc_b`, `r_dac_b`) through unchanged standard application interfaces. Still attempt and report legacy `r_sci_uart`/`r_dac` compile checks, recording the hardware-variant mismatch instead of claiming an unchanged pass. Do not add legacy-driver adapters or fabricate their different register layouts.
- RTOS ports access more than CMSIS SysTick: FreeRTOS uses `R_MPU_SPMON->SP[1]` and NMI masks when stack monitoring is selected, and low-power registers under tickless operation (`rm_freertos_port/port.c:366–379,1234–1387`). ThreadX has the same stack-monitor dependency (`rm_threadx_port/tx_initialize_low_level.c:125–129`). Default-off options must not conceal missing definitions; absent hardware must instead have truthful capability/configuration restrictions.
- MRAM already declares `flash_api_t`/`flash_cfg_t`; DAC_B already declares `dac_api_t`/`dac_cfg_t`. Preserve these correct interfaces while auditing operational contracts, errors, defaults, callback handling and extension layouts. Do not replace correctly implemented standard interfaces merely for naming consistency.
- PDM currently places all interface/configuration/implementation declarations in `inc/instances/r_pdm.h`, with hardware filter/clock/limit settings directly in `pdm_cfg_t` and no `p_extend` (`r_pdm.h:73–97,107–148`). This needs an FSP-style interface/instance split and hardware extension.

## Integration order

### 1. Freeze the actual before state and create the compatibility gate

After approval, record current changed paths, owning-source/header/MDF hashes, r008 manifest and existing pin-model hashes; preserve all current work and previous evidence. Read-only pack verification must identify the journalled candidate in the isolated support area, not assert that RA8P1 is absent. Retain current GNU 13.2.1/core/ABI/debugger/memory contracts. Run the existing relevant tests as a before checkpoint; do not misuse the pristine-baseline verifier to reject intentional edits.

Add **proposed** `tools/ra8p1/compatibility.py`, a machine-readable module census and focused `tools/test_ra8p1_compatibility.py`; retain before/after results under **proposed** `validation/ra8p1/compatibility/`. Reuse current generation, pack and regression helpers; do not build another IDE automation framework.

The census will enumerate every original FSP 5.9 HAL component and map it to RA8P1's documented IP/variant, channels, required source files, public headers, MDF/PDSC dependencies and useful conditional configurations. Cross-check hardware presence independently of current MDF provides, so incomplete metadata cannot shrink coverage. Classify each module as unchanged-compatible, capability adaptation required, genuinely absent IP/variant, or blocked with exact evidence. Hardware-present modules cannot be silently omitted. Include all translation units selected by their original PDSC, not just one conveniently compiling file.

Mandatory explicit rows: `r_ioport`, `r_cgc`, `r_wdt`, `r_iwdt`, `r_dtc`, `r_dmac`, `r_elc`, `r_icu`, `r_gpt`, `r_sci_uart`, `r_sci_b_uart`, `r_spi_b`, `r_adc_b`, `r_dac`, `r_dac_b`, `rm_freertos_port` and `rm_threadx_port`, plus every additional hardware-present stock module found by the census. Under the accepted decision, legacy `r_sci_uart`/`r_dac` are explicit negative/variant-mismatch rows, not required legacy-driver adaptations and not passes. Correct-variant success must be reported separately, including generic application use of `uart_api_t`/`dac_api_t` without target-specific branches.

Build two separately reported source sets against the real generated RA8P1 BSP:

1. Hash-verified pristine FSP 5.9 HAL/RTOS sources and matching instance/API headers: proves exactly which modules compile **unchanged**.
2. Current candidate sources/headers: proves any required capability-gated adaptations compile and link.

Use isolated build inputs referencing the generated `ra_cfg`/`ra_gen` and real CMSIS/core headers. Obtain third-party/kernel dependencies exclusively from original release packs. Never patch generated configuration to manufacture a pass, define missing register names in the harness, suppress incompatible-pointer diagnostics, or stub hardware/RTOS APIs. Preserve exact diagnostics and command lines before corrections, then repeat the same cases afterward. No compilation is claimed during planning.

### 2. Repair the device header at its generator/inventory owner

Prepare a naming/semantic map per block: baseline type/instance/member/mask name, current target spelling, documented target register, address/width/offset/stride/access, and disposition. Use existing FSP names as canonical wherever the hardware meaning matches. Emit the nested cluster types, register arrays, individual register views and `_b`/`_Pos`/`_Msk` forms that stock code consumes. Complete applicable blocks instead of stopping after the first missing identifier.

Change `tools/ra8p1/registers*.json`, `generate_device_header.py`, generated owning `R7KA8P1KF.h`, `tools/test_ra8p1_device_header.py` and its layout fixtures together. Add generator support for reviewed type/field/array views where necessary, with collision and overlap checks. Correct tests that currently forbid a legitimate baseline name instead of protecting hardware correctness. Migrate current BSP/driver references to canonical names in the same integration batch.

Do not invent aliases between incompatible IPs, registers with different side effects, security domains or CPU banks. No `bsp_compat.h`, global field-name macros, pointer casts to sibling layouts, or `#undef` shims. Equivalent names/views may coexist only inside the owning header when documented identity is proved, with equality/layout tests. Preserve distinct target register names when hardware really differs; adapt shared owners through capabilities rather than pretending absent legacy registers exist.

For every emitted public view, check `sizeof`, alignment, `offsetof`, array first/last element and stride, bitfield bytes, mask values, secure/nonsecure bases and CPU-local selection. Run native and actual CM85/CM33 compiler checks. Keep target numbers manual-derived and cited. A type cast or green compile does not establish register correctness.

Publish the first coherent header correction and immediately regenerate/clean-build CPU0 and the CPU0→CPU1 pair. Then integrate each additional block batch through its real stock-module gate; do not postpone all integration until the full census is green.

### 3. Restore driver/interface contracts and generated defaults

Keep existing FSP 5.9 shared API structs, enums, function-pointer signatures and callback constness unchanged. Device extensions belong in `p_extend`, not shared configs. Use the existing `BSP_OVERRIDE_*` mechanism only for genuine device encodings. All new capability macros must be defined consistently across the MCU set with old values preserving the prior branch.

Audit every entry point of MRAM, DAC_B, ADC_B, WDT and CGC—not just their vtable assignments—against its baseline API and analogous stock implementation. Verify Open/Close/reopen order, persistent instance state, busy/error cleanup, meaningful return codes, supported operations, callback/context/memory handling, parameter checking on/off and optional-feature paths. Do not invent start/stop/callback methods that the applicable interface does not contain.

- **MRAM:** retain `flash_api_t`, `flash_instance_t`, `flash_cfg_t` and `mram_extended_cfg_t`. Fix the confirmed behavioral gap: `R_MRAM_CallbackSet` currently always returns unsupported (`r_mram.c:455–486`). Store the Open callback/context and implement the standard setter with instance-owned callback/context/memory fields, stock parameter checks and secure/nonsecure callback-memory handling, following `r_flash_hp.c:1236–1274`. Blocking operations need not invent completion callbacks or BGO; document that distinction. Test setter-before-Open, replacement, callback/context identity and invalid nonsecure memory. Reconcile Erase/BlankCheck geometry and semantics, InfoGet, errors and unsupported flash-only commands against the manual and baseline conventions. Hardware-absent features return documented standard errors, not success stubs. Preserve zeroization/busy/protection/cache/RAM-execution safeguards, reserved write-window enforcement and disabled-by-default privileged commands. Default generation must allow safe Open/status/info/read-only use without enabling writes over code or option memory; test default Open succeeds and Write is denied until a window is deliberately reserved.
- **DAC_B:** retain `dac_api_t`, `dac_instance_t`, `dac_cfg_t`; keep voltage, trigger, pairing and calibration details in its extended config. Move optional value/justification validation in `r_dac_b.c:93–102` under `DAC_B_CFG_PARAM_CHECKING_ENABLE`, as required by FSP parameter-check conventions. With checking disabled, preserve the 16-bit DADR write convention: HM §55.2.1, p.3501 specifies which twelve bits are used for each format. Keep actual protection/calibration/ownership safeguards independent. Preserve ordinary `open/write/start/stop/close` behavior, both channels, duplicate-owner checks and usable default calibration/output settings. Add pair-level fixture checks for exclusive channel ownership rather than claiming an MDF constraint synchronizes CPU0 and CPU1. Do not add callback/read methods absent from `dac_api_t`. Treat classic `r_dac` compatibility as a separate requested census row; a passing DAC_B test alone does not satisfy it.
- **ADC_B:** retain `adc_api_t`, `adc_cfg_t`, `adc_channel_cfg_t` and the existing extended layout; target-only additions stay in `adc_b_extended_cfg_t`. Verify channel-config/read/read32/scan/calibration/callback and unsupported-operation behavior through the interface. Keep classic `r_adc` unchanged unless a specific, evidenced shared correction is necessary. Preserve existing defaults and explicit opt-in erratum constraints.
- **WDT/CGC:** retain `wdt_api_t`/`cgc_api_t` and generated standard configs. Preserve per-core WDT/OFS selection, NMI callback dispatch, shared clock ownership, valid transitions and rejection before unsafe writes. Canonical register renaming must not regress these paths.
- **PDM:** add **proposed** `inc/api/r_pdm_api.h` for common opaque control, config, callback/status/event, API and instance types; keep implementation control and **proposed** `pdm_extended_cfg_t` in `inc/instances/r_pdm.h`. Common config contains channel, IRQ/priorities, callback/context and `void const * p_extend`; hardware-specific filter/edge/format/clock/coefficient/threshold/limit settings move into the extension. Retain the present `open/start/stop/statusGet/close/callbackSet` contract, finite capture and buffer ownership—there is no baseline PDM API to imitate or a need to invent another streaming behavior. Update the implementation, tests, MDF initializers, generated guards and PDSC ownership together. Keep optional argument checks under `PDM_CFG_PARAM_CHECKING_ENABLE`; retain mandatory hardware-safety and busy-state guards independently and document the distinction. Keep the current deliberate shared-module-clock retention on Close (`r_pdm.c:240–258`), so closing one channel cannot disable another; document it rather than adding an unrelated cross-core/global reference-counting service.

For each driver, update its owning MDF declarations/includes/config templates/guards with the C contract. Preserve module/property IDs and serialized user values where possible; the PDM MDF can move values into the new extension without changing property IDs. Update only current-run first-party fixtures that explicitly constructed the old PDM layout. This intentional correction of a custom candidate API is not a change to any stock FSP 5.9 interface; document the source migration.

Default MDF validation starts with a newly added, otherwise uncustomized stack on each core, not only a heavily customized handpicked spec. Make generated PDM defaults include valid data/error vectors and priorities, extension values and board-consistent channel/edge settings; make DAC_B defaults provide a legal calibration budget and extension. Check ADC_B defaults against the existing board clock tree and use capability-gated target defaults where needed, preserving older-device output. Any unavoidable clock/pin prerequisite must produce a clear configurator requirement and a documented configuration-only recipe, never hidden application setup. Test default Open and ordinary lifecycle in production-C host fixtures, and build generated `hal_data.c`/vectors without application casts, custom register definitions or RA8P1 branches. MRAM remains safely write-disabled by default.

### 4. Capability-gated adaptations for genuine hardware differences

For each census failure, distinguish missing/wrong header vocabulary from actual changed hardware. Fix the header first. Modify a stock driver or RTOS port only for a proved hardware difference; keep the old branch intact, and record the capability, manual citation and reason pristine source cannot work. Do not hide missing support by clearing presence flags or disabling a supported option.

Preserve the distinction between a stock **source** compiling unchanged, a capability-adapted implementation, and an application still using the same standard interface. For SCI/DAC/SPI layout variants, sharing a functional API does not make legacy register code compatible. Record the accepted legacy SCI/DAC exceptions as variant mismatches; any remaining failure of a hardware-present correct variant is a blocker, never an unchanged-pass label.

RTOS checks will compile all GCC-selected port files with real original kernel headers and generated port config on both cores. Exercise default scheduling and supported low-power/tickless branches. The current RA8P1 capability has `BSP_FEATURE_BSP_HAS_SP_MON=0`; verify that hardware absence against the manual and reject unsupported stack-monitor settings rather than inventing `R_MPU_SPMON` to satisfy inactive code. Test the supported older-device stack-monitor path when a shared port changes. Follow with minimal generated FreeRTOS and ThreadX link builds, keeping CPU1 secondary startup and interrupt ownership intact. No RTOS scheduler/runtime success is implied.

### 5. Publish, rebuild and regress against one final revision

Reuse `tools/build_ra8p1_packs.py`, `tools/ra8p1/prepare_pack_resources.py`, `verify_candidate.py` and existing tests/regression tooling. Produce a new immutable candidate revision with manifest and matching archive bytes; preserve r008. Include the new PDM interface header and all changed shared-source copies in every owning pack. Continue the explicitly authorized same-FSP-version isolated-candidate workflow; do not restore stock or edit the installation manually.

Parent serializes publication against all e2 lanes. Use `embedder e2 validate mdf` on changed metadata with canary and sibling parity where affected; review diffs, install dry run, then its exact apply plan. Verify installed pack bytes, extracted support files and affected project sources; refresh only the stale layer through reviewed `packs refresh` plans. Unknown edits block replacement. Regeneration and clean builds alone are not freshness evidence.

Rebuild the BSP pair, all affected driver projects, full stock-compatibility census and minimal RTOS projects on both cores with parameter checking enabled/disabled. Build through CPU1 to maintain preceding Smart Bundle order. Independently rerun source/ELF verifier for physical part, actual compiler CPU/FPU/ABI, debugger, vectors/reset/stack, physical load-range disjointness, TCM aliases and CPU0-only option-memory ownership. Re-run both-core `board check`; preserve unchanged pin-model hashes and zero unknown pin IDs.

Reuse the six established older-device controls (RA8M1, RA6T2, RA8D1, RA4M2, RA4M1, RA0E1), adding another only when a newly changed shared owner requires it. For affected controls run real generation/clean links/checks-on/off; compare original-release and current executable/constant bytes plus relocations only for changed shared translation units under identical generated inputs/flags. Include newly adapted HAL/RTOS files in the regression coverage; do not reuse the old 108-comparison count as proof of untested changes. Keep original stock and candidate evidence separate. Unsupported devices must not acquire new-only stacks. Run focused production-C contract/layout tests and the complete host suite at the final freeze.

## Delegation after approval

Current header and API audits are read-only planning assignments; incorporate their evidence without launching duplicates. Implementation assignments will use distinct write ownership and concise changed-path/test/blocker reports:

1. **Header specialist:** register inventories, generator, owning device header and layout tests. Delivers canonical-name batches beginning with required core/stock blocks; no shared driver/BSP writes.
2. **Driver-contract specialist:** MRAM/DAC_B/PDM C/instance headers, proposed PDM API header, their MDFs and focused contract fixtures. Coordinate naming contract with header owner before edits; no shared API changes to existing interfaces.
3. **Parent/integrator:** census/harness, shared BSP/capability registry, necessary stock-driver/RTOS adaptations, metadata integration, serialized pack publication, generated builds and evidence. Delegate an independent regression runner against frozen revisions when useful; it owns only its tests/reports/control trees, never pack installation or files being edited by another owner.

Header and contract implementation can proceed in parallel; release complete source+MDF batches to integration immediately. No two writers own the same files. Stop/reassign ownership explicitly if a child needs shared changes; no blanket prohibition on necessary capability changes. Review delivered code and focused evidence before reporting a pass.

## Acceptance, reporting and risks

The final report will contain one before/after compatibility table, followed by remaining limitations and intentional changes. Table columns: item/module, interface type or canonical header contract, before result, after result (unchanged vs capability-adapted), deviation/reason, both-core generated/clean builds, older-device regression. Every mandatory module and every audited driver gets an identifiable result; the complete additional-module census is linked. Before measurements will be captured after approval, not inferred from r008's narrower successes. Report RTOS compile/link separately from runtime, parameter configurations and pack revision, plus exact diagnostics for any blocked row.

Completion requires no missing hardware-present correct-variant census rows, no unexplained naming/layout deviations, standard API-only application fixtures, usable safe defaults, fresh final artifacts and passing affected regressions. The two accepted legacy-variant mismatches remain visible exceptions and are not counted as passes. Unexpected differences or facts unavailable from permitted sources remain blockers, not aliases, stubs or disabled capability claims. No hardware results will be claimed.

Post a short current-status table after the first repaired CPU0/pair build, each corrected driver's first generated build, and completion of the expanded stock/RTOS gate; continue without waiting for acknowledgment. Keep failures, pending checks and hardware-unverified status explicit.

Main risks are the breadth of the incomplete header, legitimate incompatible IP layouts masquerading as naming errors, optional RTOS branches hiding failures, and same-version pack staleness. Counter them with the explicit census, manual-derived layout tests, pristine-vs-adapted source distinction, real RTOS dependencies/configuration coverage and three-layer freshness checks. Existing memory, zeroization, cache, NMI, ownership and MRAM scratch-safety tests remain mandatory throughout.
