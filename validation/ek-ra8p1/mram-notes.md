# EK-RA8P1 CPU0 MRAM fixture

## Scope and command protocol

The only permitted destination is `[0x0207F800, 0x02080000)`, the final 2 KiB of the CPU0 application partition, immediately below CPU1. `evidence/mram-preservation.log` records the original block (1181 non-`FF` bytes); the user authorized erasing it. Preserve that snapshot as evidence, not as a restore operation.

1. Generate the `g_bench_mram` instance with `cpu0-mram.json`, compile the fixture and dispatch the four literal commands through `bench_mram`. The r020 MDF ID is `module.driver.flash_on_mram`; it takes **decimal absolute addresses**, exclusive `write_end`, positive `timeout` (a poll budget, not a time), and `extra=disabled`. Blocking mode, no callback and no IRQ are the MDF defaults. Neither this spec nor the fixture changes option words, startup selection, security, or block protection.
2. Before flashing or arming, audit the **integrated** GNU Flat ELF and the actual application-only download against the scratch window. The linker partitions do not reserve these last 2 KiB; reject any overlapping load or live image. Check `.code_in_ram` is in initialized CPU0 SRAM (`.data`, copied by startup), `r_mram_program` and `mram_exception` execute entirely in SRAM, and `vectors` (512-byte alignment) and `pattern` (32-byte alignment) are in CPU0 SRAM. Verify the candidate driver bytes against the r020 manifest. Do not download options or allow debugger erase/program of scratch.
3. Use a clean CPU0 boot, before any `wdt-arm` or CPU1 start. Do not run another fixture between MRAM phases. CPU0/CPU1 DMAC/DTC, other bus masters and hardware/watchdog agents must not access code MRAM during programming; the fixture checks CPU1 inactive and CPU0 DMAC/DTC disabled and relies on the bench for other masters. No debugger/memory polling during programming; disconnect and confirm free-run. If halting debug or debugger write-enable remains set, the command refuses to proceed.
4. `mram-arm` checks preconditions and emits `MRAM ARMED` without touching the block. `mram-write` writes all ones through `R_MRAM_Erase(..., 1)`, verifies all 2048 bytes, then programs and verifies the pattern. At byte offset `i`, expect `(0xA5 ^ (i & 0xFF) ^ (0x1D * (i >> 8))) & 0xFF` (2048-byte SHA-256: `d4f1497df8a4f381c6ab60b7c5407fa1c8b2eea069c174d245c7d036f0a7fc7f`). Wait for `MRAM WRITE verified` and read/compare **all** 2048 bytes externally, with debugger flash/memory caching disabled. Finish external readback and release the debugger before continuing.
5. If debugger state requires a power cycle, boot the same fixture undebugged and issue `mram-resume` **instead of** `mram-arm`. Only in the initial state, it repeats the unchanged preflight and checks every byte with fresh volatile reads and the ECC status. If all bytes match the expected pattern, `MRAM RESUMED` arms cleanup only; this command never programs or erases. If the pattern is incomplete or does not match, it refuses recovery.
6. `mram-clean` separately erases to all ones and verifies all bytes before reporting `MRAM CLEAN verified`. Independently read back all 2048 final bytes as `FF`. Cleanup can also be invoked after a failed program attempt if the fixture is still running and its preflight passes. A fatal NMI/fault or a sequencer that never drains cannot safely report or recover over UART; use a board reset, establish state independently, and do not take absent logs as a pass.

## Manual and r020 checks

- RA8P1 HM Rev.1.30 §§7.2.8–9, 60.8.3, 60.9.1.2: the physical block is `0x7F800 / 2048 = 255`, beyond the startup-swap area. BPS_SEC uses bit 31 of word 7 (`0x02C9F21C`). **One PBPS bit protects four adjacent BPS bits**; PBPS_SEC uses bit 31 of word 1 (`0x02E17704`). Both bits must read 1; the fixture also requires a `CMSAMON.CMS` covering the entire block in the secure alias (HM §52.3.3.5, Table 52.1 and §52.8.11). If independent checks use non-secure option addresses, the corresponding words are `0x12C9F61C` and `0x12E17784`; the fixture does not use the non-secure alias. Unknown or protected settings are a stop condition, not grounds to override protection.
- HM §§60.4.2, 60.5.1–3, 60.5.31–39 and Table 70.124: r020's CPU0 bench uses XTAL 24 MHz with MRICLK and MRPCLK at 24 MHz and frequency notifications both 24. Read back these settings, normal program mode, MRAM prefetch off (required at ≤100 MHz), and CM85 D-cache off. On completion the r020 RAM helper drains the code buffer, restores `MRCPC1`, invalidates CM85 I-cache, and restores cache/prefetch/IRQ state. It does not modify `MRCBPROT0/1`. The fixture installs an SRAM vector table and SRAM fail-stop handler while IRQs are masked; PRIMASK alone does not mask NMI. UART output is after VTOR and interrupts are restored. Verify readback with volatile reads and check code MRAM ECC flags.
- `evidence/wdt-clock-preflight.json` recorded live MRCFREQ/MREFREQ = `0x18` on the preceding r020 build. The earlier `evidence/mram-preflight.json` used PBPS word 7 and therefore does **not** establish PBPS for this block. Repeat the read at word 1 and capture the secure attribution on the intended board. Source, mock/isolated linkage, and manual checks are not target validation.
